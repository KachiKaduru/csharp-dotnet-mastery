Before you start: can you explain, without notes, value vs reference types, what a record generates, deferred execution, and why async void is dangerous? Anything blank is what this project will expose.
How to work this
Build first, study second. Open an editor and start. Keep a gap log open beside you and write down every time you look something up, hesitate, or write something you are not confident is idiomatic. That log — probably six items, not twenty — is your actual revision list for the week.

3. Rules To Enforce

The point of this project is that invalid states should be unreachable, not merely checked for.

  • An account cannot exist without a number and an owner
  • A balance can never go negative — withdrawal and transfer must reject, not clamp
  • Deposits and withdrawals must be strictly positive
  • No transfer to the same account
  • No transfer between accounts of different currencies
  • A frozen or closed account rejects everything except a statement
  • Balance must only be changeable through the operations, never by assignment
  • Every balance change must produce a Transaction — the statement must always reconcile to the balance
The one that is harder than it looks
A transfer touches two accounts. If the credit fails after the debit succeeded, you have destroyed money. Work out how you will guarantee that a transfer either fully happens or fully does not — with no database transaction to lean on. This is the central problem of financial software, and it is worth meeting now in miniature.

5. Add One Hard Constraint

Plain CRUD teaches CRUD. Pick one of these and do it properly — the constraint is where the learning is:

  • Crash safety. Kill the process mid-transfer. On restart, the balances and the statement must still agree.
  • Concurrency. Run 100 concurrent transfers between the same two accounts using Task.WhenAll. The total across both accounts must be unchanged at the end. Find out what a race condition actually looks like.
  • Immutable history. Make Transaction genuinely append-only, and derive every balance from the transaction list rather than storing it. Then see what that costs you.

6. Then Review It

When it works, go back through it and ask:

  1. Can any code path produce an invalid Account? If yes, move validation into the constructor.
  2. Is there any public set on a balance or a transaction? Remove it.
  3. Did you use decimal everywhere money appears? Check every one.
  4. Is there a catch that swallows? A throw ex? Fix both.
  5. Is every IDisposable inside a using?
  6. Does any method exceed about twenty lines? If so, what is it doing that should be separate?
  7. Could you unit test the transfer logic without touching the console or the file system? If not, why not?
The last question is the important one
If your business rules are tangled up with Console.WriteLine and file access, they are untestable — and that is a design problem, not a testing problem. Separating decisions from I/O is the single most valuable habit this project can teach you, and it is the foundation of everything in Week 2.
