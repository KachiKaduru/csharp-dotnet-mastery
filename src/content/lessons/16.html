1. A Test

xUnit
public class AccountTests
{
    [Fact]
    public void Withdraw_WithInsufficientFunds_Throws()
    {
        // Arrange
        var account = new Account("ACC1", opening: 100m);

        // Act + Assert
        var ex = Assert.Throws<InvalidOperationException>(
            () => account.Withdraw(500m));

        Assert.Contains("Insufficient", ex.Message);
        Assert.Equal(100m, account.Balance);     // unchanged — the important part
    }
}

Name tests so a failure report reads as a sentence. MethodName_Scenario_ExpectedResult is the common convention, and it means the CI output tells you what broke without opening the file.

xUnitPurpose
[Fact]A test with no parameters
[Theory] + [InlineData]The same test over several inputs
ConstructorSetup — runs before each test
IDisposable.DisposeTeardown
IClassFixture<T>Shared expensive setup across a class

xUnit creates a new instance of the test class for every test, so there is no shared state to leak between them. That is a deliberate design difference from NUnit and MSTest.

2. Theories — One Test, Many Cases

table-driven
[Theory]
[InlineData(0)]
[InlineData(-1)]
[InlineData(-100.50)]
public void Deposit_WithNonPositiveAmount_Throws(decimal amount)
{
    var account = new Account("ACC1");
    Assert.Throws<ArgumentOutOfRangeException>(() => account.Deposit(amount));
}

[Theory]
[InlineData(100, 0.015, 1.50)]
[InlineData(1000, 0.015, 15.00)]
[InlineData(0, 0.015, 0)]
public void Fee_IsCalculatedCorrectly(decimal amount, decimal rate, decimal expected)
{
    Assert.Equal(expected, FeeCalculator.Calculate(amount, rate));
}

Each case is reported as a separate test, so you see exactly which input failed. This is the cheapest way to cover boundaries — zero, negative, maximum, empty, null.

3. Moq — Faking Dependencies

isolating the unit under test
[Fact]
public async Task Transfer_WhenCoreTimesOut_DoesNotDebitTwice()
{
    // Arrange
    var core = new Mock<ICoreBankingClient>();
    core.Setup(c => c.SendAsync(It.IsAny<TransferRequest>(), It.IsAny<CancellationToken>()))
        .ThrowsAsync(new TimeoutException());

    var accounts = new Mock<IAccountRepository>();
    var service = new TransferService(core.Object, accounts.Object,
                                      NullLogger<TransferService>.Instance);

    // Act
    await Assert.ThrowsAsync<TimeoutException>(
        () => service.TransferAsync(request, default));

    // Assert — verify the interaction, not just the result
    accounts.Verify(a => a.DebitAsync(It.IsAny<string>(), It.IsAny<decimal>(),
                                      It.IsAny<CancellationToken>()),
                    Times.Once);
}
MoqDoes
Setup(...).Returns(x)Define a return value
.ReturnsAsync(x)Same, for a Task<T>
.ThrowsAsync(ex)Simulate a failure — often the most valuable test you can write
It.IsAny<T>()Match any argument
It.Is<T>(x => ...)Match arguments satisfying a predicate
Verify(..., Times.Once)Assert a call happened exactly once
The tests worth writing are the failure tests
Anyone can test that a transfer succeeds. The valuable tests are the ones you cannot easily produce by hand: the core times out, the database throws mid-operation, the response is malformed, the same request arrives twice. Mocks exist primarily so you can simulate the failures that are hard to arrange for real.
Do not mock what you do not own
Mocking HttpClient, DbContext or a third-party SDK produces brittle tests that assert your assumptions about someone else's library rather than its behaviour. Wrap it in your own thin interface and mock that — or test against the real thing in an integration test.

4. Integration Tests

Unit tests check a class. Integration tests check that the pieces actually fit — routing, model binding, DI wiring, serialisation, middleware. In ASP.NET Core they are genuinely easy:

the whole app, in memory
public class AccountsApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public AccountsApiTests(WebApplicationFactory<Program> factory)
        => _client = factory.CreateClient();

    [Fact]
    public async Task Get_UnknownAccount_Returns404()
    {
        var response = await _client.GetAsync("/api/accounts/does-not-exist");
        Assert.Equal(HttpStatusCode.NotFound, response.StatusCode);
    }

    [Fact]
    public async Task Post_WithBlankOwner_Returns400WithFieldError()
    {
        var response = await _client.PostAsJsonAsync("/api/accounts",
            new { owner = "", currency = "NGN", opening = 100 });

        Assert.Equal(HttpStatusCode.BadRequest, response.StatusCode);
        var problem = await response.Content.ReadFromJsonAsync<ValidationProblemDetails>();
        Assert.Contains("Owner", problem!.Errors.Keys);
    }
}

WebApplicationFactory<Program> boots your real application in memory — real DI, real middleware, real routing — with no network and no deployment. Override registrations to swap the database for an in-memory or containerised one.

5. What To Test, And What Not To

Test thisDo not bother
Business rules and calculationsAuto-properties and trivial getters
Boundaries: zero, negative, maximum, empty, nullFramework behaviour — that [Required] works
Error paths and failure handlingThird-party library internals
Anything that has broken beforeImplementation details that will change
Contracts at a boundary — status codes, response shapePrivate methods directly
Test behaviour, not implementation
A test that asserts what the code does survives refactoring. A test that asserts how it does it breaks every time you tidy anything, and a suite like that stops being a safety net and becomes a reason not to improve the code. If renaming a private method breaks a test, that test was coupled to the wrong thing.

The practical check: could this test still pass if I rewrote the internals and kept the behaviour? If not, it is testing the wrong layer.

On coverage: it measures lines executed, not correctness. A hundred percent coverage with no assertions proves nothing, and chasing the last few percent usually means testing generated code. Use it to find untested areas, never as a target.
