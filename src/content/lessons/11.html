1. The Whole Startup, In One File

Program.cs
var builder = WebApplication.CreateBuilder(args);

// ── 1. REGISTER services (the DI container) ──
builder.Services.AddControllers();
builder.Services.AddScoped<IAccountRepository, SqlAccountRepository>();
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddHttpClient<CoreBankingClient>();

var app = builder.Build();

// ── 2. BUILD the request pipeline (middleware) ──
app.UseExceptionHandler("/error");
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();

Two distinct phases, and the distinction matters. Before Build() you register what the application has. After Build() you declare what a request goes through. Trying to add a service after Build() throws.

2. Dependency Injection Is Built In

There is no separate container to install. A class declares what it needs in its constructor and the framework supplies it.

constructor injection
public class AccountService
{
    private readonly IAccountRepository _repo;
    private readonly ILogger<AccountService> _logger;

    public AccountService(IAccountRepository repo, ILogger<AccountService> logger)
    {
        _repo = repo;
        _logger = logger;
    }
}

Nobody ever writes new AccountService(...). The container sees the constructor, resolves each parameter from its registrations, and builds the whole graph.

Why this matters beyond convenience
The class depends on IAccountRepository, not on a SQL implementation. That single fact is what makes it testable — a test constructs it with a fake — and what lets you swap the database without touching business logic. Dependency injection is not plumbing; it is the mechanism that keeps the interesting code independent of the boring code.

3. The Three Lifetimes

The captive dependency bug
Never inject a Scoped service into a Singleton. The singleton is created once and holds that instance for the lifetime of the application — so a request-scoped DbContext ends up shared across every subsequent request, long after its own request ended. Symptoms are disposed-object exceptions and data from one user appearing in another's response. ASP.NET Core detects this at startup in development; do not suppress the error, fix the lifetime.

When a singleton genuinely needs scoped work, inject IServiceScopeFactory and create a scope per unit of work.

4. Middleware — The Request Pipeline

Every request passes through an ordered chain. Each piece can act on the way in, pass control onward, and act again on the way out.

Request  ▸  Exception handler  ▸  HTTPS  ▸  Auth  ▸  Authorization  ▸  Endpoint
                     ▾                 ▾        ▾            ▾              ▾
Response ◂──────────────────────────────────────────────────────────────
custom middleware
app.Use(async (context, next) =>
{
    var sw = System.Diagnostics.Stopwatch.StartNew();

    await next(context);          // everything downstream happens here

    logger.LogInformation("{Method} {Path} -> {Status} in {Ms}ms",
        context.Request.Method, context.Request.Path,
        context.Response.StatusCode, sw.ElapsedMilliseconds);
});
Order is behaviour, not style
The pipeline runs in registration order. UseAuthorization before UseAuthentication means authorisation runs before anyone has been identified, so every authenticated endpoint rejects valid requests. UseExceptionHandler registered last cannot catch anything registered before it. When something inexplicable happens in ASP.NET Core, check the middleware order first — it is the most common cause.

Note also: calling next is optional. Middleware that does not call it short-circuits the pipeline and returns immediately — which is exactly how caching and rate limiting work.

5. Configuration

appsettings.json
{
  "ConnectionStrings": {
    "Default": "Server=localhost;Database=minibank;Trusted_Connection=True;"
  },
  "CoreBanking": {
    "BaseUrl": "https://core.internal/api",
    "TimeoutSeconds": 5,
    "MaxRetries": 3
  }
}

Sources are layered, each overriding the previous: appsettings.json, then appsettings.{Environment}.json, then environment variables, then command-line arguments. That is how one build runs in every environment.

the options pattern — preferred
public class CoreBankingOptions
{
    public required string BaseUrl { get; init; }
    public int TimeoutSeconds { get; init; } = 5;
    public int MaxRetries { get; init; } = 3;
}

// register
builder.Services.Configure<CoreBankingOptions>(
    builder.Configuration.GetSection("CoreBanking"));

// consume — strongly typed, injected
public class CoreBankingClient(IOptions<CoreBankingOptions> options)
{
    private readonly CoreBankingOptions _o = options.Value;
}

Prefer this over reading IConfiguration["CoreBanking:BaseUrl"] everywhere: you get types, defaults, validation, and a single place that documents what the application can be configured with.

Secrets never go in appsettings.json
It is committed to source control. Use dotnet user-secrets in development and environment variables or a secret store in production. A connection string with a password in a repository is a security incident, and rotating it afterwards is considerably more work than doing this correctly the first time.
