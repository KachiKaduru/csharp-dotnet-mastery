Recall first — no notes
Without looking: the three DI lifetimes, what causes N+1, why a JWT cannot be revoked, and what makes a test coupled to implementation.

1. What You Are Building

MiniBank as an HTTP API. Three projects, as set up on the setup page:

MiniBank.sln
├── MiniBank.Core      ← domain types and business rules. No ASP.NET, no EF
├── MiniBank.Api       ← controllers, DI, middleware, EF, auth
└── MiniBank.Tests     ← unit tests for Core, integration tests for Api
The constraint that teaches the most
MiniBank.Core must not reference ASP.NET Core or EF Core at all. Business rules depend on nothing but the language. If a rule needs data, it takes it as a parameter or depends on an interface that Core defines and Api implements. That single restriction forces the dependency direction that makes the whole thing testable, and it is the practical core of every "clean architecture" article you will read.

3. Requirements Checklist

  • DTOs everywhere. No EF entity appears in a request or a response signature
  • Validation via annotations for shape, service layer for business rules
  • One exception-handling middleware mapping domain exceptions to status codes and ProblemDetails. No try/catch in any controller
  • EF Core with migrations, HasPrecision(18,2) on every money column, and a unique index on account number
  • JWT auth with 15-minute tokens, all four validation flags on, a policy for the admin report
  • Passwords via PasswordHasher. Identical error message for unknown user and wrong password
  • Structured logging with a scope carrying the transfer reference, and durations on external calls
  • Pagination on the transactions endpoint, with the total count returned
  • Tests: unit tests for every rule in Core, integration tests via WebApplicationFactory for each endpoint's status codes
  • Secrets in user-secrets, never in appsettings.json

4. Pick One Hard Constraint

Plain CRUD teaches CRUD. The constraint is where the learning is — do one of these properly:

  • Idempotent transfers. Accept an Idempotency-Key header. The same key replayed must return the original result and must not move money twice. Then prove it with a test that fires the same request twice concurrently.
  • Optimistic concurrency. Add a rowversion to Account. Two simultaneous transfers from the same account must not both succeed against a stale balance. Handle DbUpdateConcurrencyException and decide what the client sees.
  • Resilience. Put a fake core banking service behind the transfer endpoint with configurable latency and failure. Add timeout, retry and circuit breaker, and make retries safe. Prove with a test that a timeout does not double-debit.
The one that will teach you the most
Idempotency. It forces you to confront the fact that a timeout means unknown, not failed — and that retrying an unknown is how money gets moved twice. Every real payment system is built around this problem.

5. Review It Before You Call It Done

  1. Does MiniBank.Core reference ASP.NET Core or EF? If so, the dependency direction is inverted
  2. Is there a single EF entity in a controller signature?
  3. Any try/catch in a controller? Any throw ex? Any empty catch?
  4. Log the SQL and exercise every endpoint. How many queries per request? Any N+1?
  5. Is decimal used for every monetary value, with precision configured?
  6. Is any service a Singleton that depends on something Scoped?
  7. Does any log line contain an account number, a token, or a serialised request object?
  8. Can you run the whole suite and have it pass with no database present?
  9. Could a new developer run this from your README alone?

6. Interview Simulation

Answer these out loud, from memory. Explaining is a harder test than recognising, and it is the one that reveals what you actually understand.

About the language

  1. Value types versus reference types, and a bug caused by confusing them
  2. Why decimal and not double for money
  3. What a record generates, and when you would use a class instead
  4. What deferred execution is, and a problem it has caused you
  5. What problem async solves — and what it does not
  6. Why async void is dangerous

About the framework

  1. Explain dependency injection and why the framework includes it
  2. The three lifetimes, and what a captive dependency is
  3. What middleware is, and a concrete bug caused by wrong ordering
  4. Why DTOs rather than entities — give three reasons
  5. 401 versus 403
  6. What a DbContext is, and why it is Scoped
  7. What the N+1 problem is and how you would find it

About judgement — the ones that actually matter

  1. Walk me through this project. What was the hardest decision?
  2. What would you change if it had to handle 10,000 transfers a second?
  3. How did you make sure a transfer cannot lose money?
  4. What is the weakest part of your code, and why did you leave it?
  5. How would you debug a report that transfers are "sometimes slow"?
  6. What did you get wrong while building this, and how did you find out?
The last two are the real questions
Anyone can recite the three lifetimes. Describing something you got wrong, how you discovered it, and what you changed demonstrates that you have actually built something and that you learn from it — which is the thing being assessed. Have a real answer ready, and do not make it a humblebrag.

7. Then Keep Going

If you want to carry this further, in rough order of value: containerise it and run it against a real database in Docker; add a CI pipeline that builds, tests and reports coverage; add OpenAPI documentation; add rate limiting; add distributed tracing with OpenTelemetry; deploy it somewhere with a URL that works.

That last one is worth more than the rest. A deployed thing you can show, explain and defend is the strongest evidence of skill there is.
