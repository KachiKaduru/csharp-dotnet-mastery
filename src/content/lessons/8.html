The one idea
Async does not make anything faster. It frees the thread while you wait. A web server has a limited pool of threads. If each request blocks a thread for 200ms waiting on a database, your throughput ceiling is set by the pool size, not by your code. Async lets that thread serve other requests while the database works, so the same hardware handles far more concurrent requests.

1. The Problem It Solves

blocking vs non-blocking
// blocking: this thread sits idle for 200ms, doing nothing, serving nobody
public decimal GetBalance(string account)
{
    var response = _http.Get($"/accounts/{account}");   // thread parked here
    return Parse(response);
}

// async: the thread is returned to the pool while the network call is in flight
public async Task<decimal> GetBalanceAsync(string account)
{
    var response = await _http.GetAsync($"/accounts/{account}");
    return Parse(response);
}

Note what is not happening: no new thread is created. The work is being done by the network card and the remote server. Async is about I/O you are waiting on — network calls, database queries, file access. For CPU-bound work it buys you nothing on its own.

2. Task and Task<T>

TypeMeans
TaskAn operation in progress that returns nothing. The async void
Task<T>An operation in progress that will produce a T
ValueTask<T>An optimisation for hot paths that usually complete synchronously. Ignore until you measure

A Task is a promise of a future result. await unwraps it — suspending the method until the task completes, then continuing with the value.

the rules of thumb
public async Task<decimal> GetAsync() { ... }   // returns a value
public async Task SaveAsync() { ... }            // returns nothing
public async void Fire() { ... }                 // ALMOST ALWAYS WRONG — see below
Never write async void
An async void method cannot be awaited, so the caller cannot know when it finished — and an exception thrown inside it cannot be caught by the caller. It escapes to the runtime and crashes the process. The single exception is an event handler, whose signature forces it. Everywhere else, return Task.

3. async All The Way Up

Async is viral by design. If a method awaits, it must be async, and so must its callers.

the shape
// controller
public async Task<IActionResult> Get(string id)
    => Ok(await _service.GetBalanceAsync(id));

// service
public async Task<decimal> GetBalanceAsync(string id)
    => await _repository.FindBalanceAsync(id);

// repository
public async Task<decimal> FindBalanceAsync(string id)
    => await _db.Accounts.Where(a => a.Id == id).Select(a => a.Balance).FirstAsync();

By convention, async methods end in Async. It is a convention, not a rule, but universal — and it makes the viral boundary visible at a glance.

4. The Deadlock You Will Cause Exactly Once

Never block on async code
var balance = GetBalanceAsync(id).Result;       // deadlock risk
var balance = GetBalanceAsync(id).GetAwaiter().GetResult();   // same
GetBalanceAsync(id).Wait();                     // same
In a context with a synchronisation context — classic ASP.NET, WPF, WinForms — the continuation needs the thread you are blocking on in order to finish. It waits for you; you wait for it; the request hangs forever. The fix is to await, all the way up. If you are stuck at a non-async boundary, make that boundary async.

Modern ASP.NET Core has no synchronisation context, so this particular deadlock is less likely there — but blocking still burns a pool thread, which defeats the entire purpose. The habit is the same either way.

5. Doing Things At The Same Time

await in sequence is sequential. If calls do not depend on each other, start them all and then await:

sequential vs concurrent
// 600ms total — three 200ms calls, one after another
var a = await GetBalanceAsync("1");
var b = await GetBalanceAsync("2");
var c = await GetBalanceAsync("3");

// ~200ms total — all three in flight together
var taskA = GetBalanceAsync("1");      // note: no await, so it starts
var taskB = GetBalanceAsync("2");
var taskC = GetBalanceAsync("3");

var results = await Task.WhenAll(taskA, taskB, taskC);
MethodCompletes when
Task.WhenAllEvery task finishes. Throws if any failed
Task.WhenAnyThe first task finishes — useful for timeouts and racing replicas
Task.DelayAfter a duration. The async Thread.Sleep
Task.FromResultImmediately — for returning a known value from an async signature
WhenAll and exceptions
If several tasks fail, await Task.WhenAll(...) rethrows only the first exception. The others are still there, on the task's AggregateException — so if you need them all, inspect task.Exception.InnerExceptions rather than relying on the catch.

6. Cancellation

Long-running work should be interruptible. CancellationToken is the standard mechanism, and ASP.NET Core supplies one that fires when the client disconnects.

pass it down, always
public async Task<decimal> GetBalanceAsync(string id, CancellationToken ct)
{
    var response = await _http.GetAsync($"/accounts/{id}", ct);
    ct.ThrowIfCancellationRequested();
    return Parse(await response.Content.ReadAsStringAsync(ct));
}

// a timeout, expressed as cancellation
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(3));
try { await GetBalanceAsync(id, cts.Token); }
catch (OperationCanceledException) { /* timed out */ }

Take a CancellationToken as the last parameter and pass it to everything you call. A method that ignores it cannot be stopped, which means a disconnected client's work keeps consuming resources to produce a response nobody will read.

7. The Mistakes, Collected

MistakeConsequence
async voidExceptions crash the process; caller cannot await
.Result / .Wait()Deadlock, or a wasted pool thread
Awaiting in a loop when calls are independentLatency adds up instead of overlapping
Not passing CancellationTokenWork cannot be stopped
Task.Run around I/OBurns a thread to wait — the opposite of the goal
Forgetting to awaitFire-and-forget: exceptions vanish silently. The compiler warns — heed it
Task.Run is for CPU work only
Task.Run moves work to a pool thread. That is right for a heavy calculation blocking a UI, and wrong for I/O — wrapping an HTTP call in Task.Run occupies a thread to sit and wait, which is precisely what async exists to avoid.
