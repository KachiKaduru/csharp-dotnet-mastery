1. A Delegate Is A Typed Reference To A Method

the explicit form
public delegate decimal FeeCalculator(decimal amount);   // declares a SHAPE

static decimal FlatFee(decimal amount) => 50m;
static decimal PercentFee(decimal amount) => amount * 0.015m;

FeeCalculator calc = FlatFee;        // store a method in a variable
Console.WriteLine(calc(1000m));      // 50

calc = PercentFee;                   // swap the behaviour at runtime
Console.WriteLine(calc(1000m));      // 15

That is the whole idea: behaviour as data. A variable holding a method you can pass to another method, store in a field, or choose at runtime.

2. You Rarely Declare One — Use Func and Action

.NET ships generic delegate types that cover almost every shape, so custom delegate declarations are now uncommon.

TypeShapeExample
Actionnothing → nothing() => Console.WriteLine("hi")
Action<T>T → nothinga => Log(a)
Func<T>nothing → T() => DateTime.UtcNow
Func<T, R>T → Ra => a.Balance
Func<T, U, R>T, U → R(a, b) => a + b
Predicate<T>T → boola => a.IsActive

In Func, the last type parameter is the return type. Func<string, int, bool> takes a string and an int and returns a bool. Action has no return type at all.

the same thing, without a custom delegate
Func<decimal, decimal> calc = amount => amount * 0.015m;

public decimal Apply(decimal amount, Func<decimal, decimal> fee) => amount + fee(amount);

var total = Apply(1000m, a => a * 0.015m);   // strategy passed in at the call site

3. Lambdas

forms
x => x * 2                      // one parameter, expression body
(x, y) => x + y                 // two parameters
()  => DateTime.UtcNow          // none
x => { var y = x * 2; return y + 1; }        // statement body
(decimal x) => x * 2            // explicit type, when inference fails
static x => x * 2               // guarantees no capture — see closures below

A lambda is just an inline method with the ceremony removed. The compiler infers the parameter types from the delegate it is being assigned to, which is why a => a.Balance works without saying what a is.

Method group conversion — when the lambda does nothing but call an existing method, pass the method itself:

accounts.Select(a => a.ToString());   // lambda
accounts.Select(FormatAccount);        // method group — cleaner when it fits
names.ForEach(Console.WriteLine);      // very common form

4. Closures — Powerful And Occasionally Surprising

A lambda can use variables from the enclosing scope. It captures the variable, not a copy of its value.

the classic trap
var actions = new List<Action>();

for (int i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));    // captures i, the variable

foreach (var a in actions) a();                 // prints 3, 3, 3 — not 0, 1, 2

All three lambdas captured the same i, and by the time they run the loop has finished and i is 3. The fix is a fresh variable per iteration:

the fix
for (int i = 0; i < 3; i++)
{
    var captured = i;                           // new variable each iteration
    actions.Add(() => Console.WriteLine(captured));
}                                               // prints 0, 1, 2

foreach (var i in Enumerable.Range(0, 3))       // foreach already gives a fresh variable
    actions.Add(() => Console.WriteLine(i));    // prints 0, 1, 2
Why C# allows what Java forbids
Java requires captured locals to be effectively final, which makes this bug impossible but also makes some patterns awkward. C# captures the variable itself, which is more flexible and puts the correctness burden on you. The static modifier on a lambda tells the compiler to reject any capture — useful when you want that guarantee in a hot path.

The injectable-clock trick
A class that calls DateTime.UtcNow directly is painful to test, because you cannot control the answer. Inject Func<DateTime> now instead: production passes () => DateTime.UtcNow, a test passes () => new DateTime(2026, 1, 1). One delegate removes the entire problem.

6. Events

An event is a delegate with restrictions: outside code may only subscribe and unsubscribe, never invoke or replace the whole list.

publisher and subscriber
public class AccountService
{
    public event Action<string, decimal>? BalanceChanged;

    public void Deposit(string account, decimal amount)
    {
        // ... do the work ...
        BalanceChanged?.Invoke(account, amount);   // ?. because it is null with no subscribers
    }
}

var service = new AccountService();
service.BalanceChanged += (acct, amt) => Console.WriteLine($"{acct} +{amt}");
service.BalanceChanged += (acct, amt) => _audit.Record(acct, amt);   // many subscribers

+= subscribes and -= unsubscribes. An event with no subscribers is null, so ?.Invoke rather than a plain call.

Events leak memory
Subscribing creates a reference from the publisher to the subscriber. If the publisher outlives the subscriber and you never -=, the subscriber can never be collected. In long-lived objects, always unsubscribe — commonly in Dispose. In modern server code, prefer explicit messaging or dependency injection over events for exactly this reason.
