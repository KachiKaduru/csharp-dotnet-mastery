2. What A JWT Actually Is

Three base64url-encoded segments separated by dots:

eyJhbGciOiJIUzI1NiJ9  .  eyJzdWIiOiIxMjMiLCJyb2xlIjoiYWRtaW4ifQ  .  SflKxwRJSMeKKF2QT4
      header                        payload (claims)                      signature
SegmentContains
HeaderThe signing algorithm and token type
PayloadClaims: sub (subject), exp (expiry), iss, aud, roles, plus anything you add
SignatureHeader and payload signed with a secret or private key
A JWT is signed, not encrypted
Anyone holding the token can read every claim in it — paste one into jwt.io and see. The signature proves it has not been altered; it does nothing to hide the contents.

So: never put anything sensitive in a JWT. No passwords, no account numbers, no PII, no internal flags you would not show the user. Put an identifier and the claims needed for authorisation decisions, and look the rest up.

The other consequence of signing is why JWTs scale: any server with the key can validate a token without a database lookup or shared session store. That is also the downside — you cannot revoke one. Until it expires, it is valid. Hence short lifetimes (minutes) plus a refresh token you can revoke.

3. Issuing A Token

TokenService.cs
public string CreateToken(User user)
{
    var claims = new List<Claim>
    {
        new(JwtRegisteredClaimNames.Sub, user.Id.ToString()),
        new(ClaimTypes.Name, user.Username),
        new(ClaimTypes.Role, user.Role)              // drives role-based authorisation
    };

    var key = new SymmetricSecurityKey(
        Encoding.UTF8.GetBytes(_options.SigningKey));

    var token = new JwtSecurityToken(
        issuer:   _options.Issuer,
        audience: _options.Audience,
        claims:   claims,
        expires:  DateTime.UtcNow.AddMinutes(15),    // SHORT
        signingCredentials: new SigningCredentials(key, SecurityAlgorithms.HmacSha256));

    return new JwtSecurityTokenHandler().WriteToken(token);
}

4. Validating It

Program.cs
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer           = true,
            ValidateAudience         = true,
            ValidateLifetime         = true,
            ValidateIssuerSigningKey = true,          // all four: non-negotiable
            ValidIssuer   = cfg["Jwt:Issuer"],
            ValidAudience = cfg["Jwt:Audience"],
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(cfg["Jwt:SigningKey"]!)),
            ClockSkew = TimeSpan.FromSeconds(30)      // default is 5 minutes
        };
    });

builder.Services.AddAuthorization();

// ... after Build()
app.UseAuthentication();
app.UseAuthorization();
Turning off validation is how tokens get forged
Every Validate* flag above defaults to true for a reason. Setting ValidateIssuerSigningKey = false means any signature is accepted, so anyone can mint a token claiming to be an administrator. People disable these to make a local test pass and then ship it. Also note the default ClockSkew of five minutes — an expired token stays valid for up to five extra minutes unless you narrow it.

5. Protecting Endpoints

attributes and policies
[Authorize]                                   // any authenticated user
public class AccountsController : ControllerBase
{
    [HttpGet]
    public IActionResult List() => Ok();

    [Authorize(Roles = "Admin")]              // role required
    [HttpDelete("{id}")]
    public IActionResult Delete(int id) => NoContent();

    [AllowAnonymous]                          // opt back out
    [HttpGet("public-rates")]
    public IActionResult Rates() => Ok();
}

Roles get coarse quickly. Policies express the actual rule:

policy-based authorisation
builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("CanApproveTransfers", p =>
        p.RequireAuthenticatedUser()
         .RequireClaim("department", "treasury")
         .RequireAssertion(ctx =>
             ctx.User.HasClaim(c => c.Type == "approval_limit") &&
             decimal.Parse(ctx.User.FindFirst("approval_limit")!.Value) >= 1_000_000m));
});

[Authorize(Policy = "CanApproveTransfers")]
public IActionResult Approve(int id) => Ok();
Prefer policies to roles
Roles = "Admin" scatters the definition of what an admin may do across every controller. A named policy puts the rule in one place, gives it a name that matches the business language, and means a change to the rule is a change in one file. Reading [Authorize(Policy = "CanApproveTransfers")] also tells a reviewer what the endpoint is for.

Inside an action, the current user is on User:

var userId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
var isAdmin = User.IsInRole("Admin");

6. Passwords

Never store a password, and never hash one yourself
Not plaintext, not encrypted, not MD5 or SHA-256. Those hashes are fast, which is exactly the wrong property — a GPU tries billions per second. You need a deliberately slow algorithm with a per-user salt and a tunable work factor: bcrypt, scrypt, Argon2, or ASP.NET Core's built-in PBKDF2 implementation.
use the framework's hasher
var hasher = new PasswordHasher<User>();

user.PasswordHash = hasher.HashPassword(user, plainPassword);   // salted, iterated

var result = hasher.VerifyHashedPassword(user, user.PasswordHash, attempt);
if (result == PasswordVerificationResult.Success) { /* ... */ }

Two more rules that matter as much as the hashing:

  • Never reveal which half was wrong. "Invalid username or password" for both cases — otherwise you have built a username enumerator.
  • Rate limit and lock out. Correct hashing does not help if an attacker gets unlimited attempts.

For anything beyond a simple case, use ASP.NET Core Identity rather than building it. It handles hashing, lockout, email confirmation, two-factor and token generation — all areas where a subtle mistake is a breach.
