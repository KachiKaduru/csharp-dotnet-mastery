1. The Mechanics

try / catch / finally
try
{
    var result = ProcessTransfer(request);
}
catch (InsufficientFundsException ex)      // most specific first
{
    _logger.LogWarning(ex, "Declined transfer {Ref}", request.Reference);
    return Declined(ex.Message);
}
catch (HttpRequestException ex)            // transport failure
{
    _logger.LogError(ex, "Core banking unreachable for {Ref}", request.Reference);
    throw;                                 // cannot handle it here — pass it up
}
finally
{
    _metrics.RecordAttempt();              // runs whether or not it threw
}

Catch blocks are tested top to bottom, so order from most specific to least. A catch (Exception) above a specific one makes the specific one unreachable — the compiler will tell you.

finally runs on success, on exception, and on an early return. It is for releasing things.

2. The Hierarchy You Need

ExceptionMeans
ArgumentExceptionA parameter value is wrong
ArgumentNullExceptionA required parameter was null
ArgumentOutOfRangeExceptionA parameter is outside its valid range
InvalidOperationExceptionThe call is wrong for the current state — e.g. withdrawing from an empty account
NullReferenceExceptionYou dereferenced null. Always a bug — never catch this, fix it
KeyNotFoundExceptionDictionary key absent
TimeoutException / TaskCanceledExceptionAn operation did not finish in time
HttpRequestExceptionAn HTTP call failed at the transport level
Argument or InvalidOperation?
If the caller passed something wrong, it is an Argument* exception. If the arguments are fine but the object is in the wrong state for this call, it is InvalidOperationException. Choosing correctly tells whoever reads the log whether to look at the call site or at the sequence of operations.

3. using — Deterministic Cleanup

Garbage collection handles memory, but not file handles, sockets or database connections. Anything holding one of those implements IDisposable, and using guarantees it is released.

three forms
// classic block
using (var conn = new SqlConnection(cs))
{
    conn.Open();
}   // Dispose() called here, exception or not

// declaration form (C# 8+) — disposed at the end of the enclosing scope
using var conn = new SqlConnection(cs);
conn.Open();

// async disposal
await using var conn = new SqlConnection(cs);

using is a try/finally in disguise. A connection leaked in a loop will exhaust the pool and the symptom is a timeout, usually under load and never in testing.

4. Custom Exceptions

a domain exception worth having
public class InsufficientFundsException : Exception
{
    public string AccountNumber { get; }
    public decimal Requested { get; }
    public decimal Available { get; }

    public InsufficientFundsException(string account, decimal requested, decimal available)
        : base($"Account {account}: requested {requested:N2}, available {available:N2}")
    {
        AccountNumber = account;
        Requested = requested;
        Available = available;
    }
}

Write one when callers need to react differently to this failure, and carry the data they need to do so as properties. If nobody will ever catch it specifically, use a built-in type — a custom exception nobody distinguishes is just a longer name.

5. The Four Things Not To Do

1. Swallowing
try { Process(); } catch { }     // never
The error is gone. No log, no signal, and the program carries on in a state you did not plan for. This is how a bug survives for a year. If you genuinely must continue, log it and say why in a comment.
2. Losing the stack trace
catch (Exception ex) { throw ex; }    // resets the trace to HERE
catch (Exception ex) { throw; }        // preserves where it actually came from
throw ex; rewrites the origin to this line, discarding the frames below it — so the log points at your catch block instead of at the bug. Bare throw; rethrows the original. If you need to add context, wrap it: throw new ProcessingException("...", ex); and the original is preserved as InnerException.
3. Exceptions as control flow
Expected outcomes are not exceptional. A customer having insufficient funds is a normal business result; use a return value or a result type. Exceptions are expensive to throw and, more importantly, they hide the normal path from whoever reads the code. The Try... pattern exists for exactly this.
4. Catching what you cannot handle
Only catch an exception if you can do something useful — retry, substitute a default, add context, translate it for a caller. Catching to log and continue, with no recovery, usually means the caller is now working with invalid data. Let it propagate to a layer that can decide.

6. Exception Filters

when — catch conditionally
try { await CallCoreBanking(); }
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.TooManyRequests)
{
    await BackOffAndRetry();
}
catch (HttpRequestException ex) when (ex.StatusCode >= HttpStatusCode.InternalServerError)
{
    FailOver();
}

Subtle but real advantage over an if inside the catch: if the filter is false the exception is never caught, so the stack is left untouched for an outer handler and the debugger still breaks at the original throw site.

7. Where To Handle Things

The practical architecture: throw low, catch high. Domain code throws precise exceptions and does not catch. One place near the boundary — a middleware or a global handler — translates exceptions into responses.

one place, not fifty
app.UseExceptionHandler(...);   // ASP.NET Core: covered on the API page

That keeps business logic free of HTTP concerns, guarantees consistent error responses, and means a new exception type does not require edits in every controller.
