1. Never new HttpClient() Per Call

It looks harmless and is a well-known production incident waiting to happen: each HttpClient holds its own socket pool, and disposing one does not release the underlying connection immediately — under load you exhaust available sockets and every outbound call starts failing.

register a typed client instead
builder.Services.AddHttpClient<CoreBankingClient>(client =>
{
    client.BaseAddress = new Uri(builder.Configuration["CoreBanking:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(5);
});

public class CoreBankingClient(HttpClient http)
{
    public async Task<AccountDto?> GetAccountAsync(string number, CancellationToken ct) =>
        await http.GetFromJsonAsync<AccountDto>($"/accounts/{number}", ct);
}

AddHttpClient hands socket lifetime management to the framework's IHttpClientFactory, and the typed client gets DI'd into whatever service needs it — same shape as any other constructor-injected dependency.

2. Retries & Circuit Breakers With Polly

A transient network blip should not become a user-facing error, but retrying blindly can turn one slow dependency into a cascading outage. Polly gives you both halves.

wire resilience onto the typed client
builder.Services.AddHttpClient<CoreBankingClient>(/* ... */)
    .AddResilienceHandler("core-banking", b =>
    {
        b.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true                 // avoid every caller retrying in lockstep
        });
        b.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,
            SamplingDuration = TimeSpan.FromSeconds(30),
            BreakDuration = TimeSpan.FromSeconds(15)
        });
    });
Only retry what is safe to retry
A GET is naturally safe to retry. A POST that initiates a transfer is not — if the first request actually succeeded and only the response was lost, a retry can double the transfer. Either avoid retrying non-idempotent writes, or make the downstream call idempotent first (next section). This is one of the few places where "just add retries" is actively dangerous instead of merely wasteful.

The circuit breaker matters just as much as the retry: once a dependency is failing consistently, stop hammering it and fail fast for a cooldown period. That protects the struggling dependency and keeps your own service responsive instead of every request queuing behind a timeout.

3. Idempotency Keys

The standard fix for "is it safe to retry this POST": the caller generates a unique key per logical operation and sends it on every attempt, including retries.

var request = new HttpRequestMessage(HttpMethod.Post, "/transfers")
{
    Content = JsonContent.Create(transferRequest)
};
request.Headers.Add("Idempotency-Key", transferId.ToString());   // same key on every retry

var response = await http.SendAsync(request, ct);

A well-built downstream service stores the key, and if it sees the same key twice, returns the original result instead of processing the transfer again. If you are the one building the receiving endpoint — which you will be, on this kind of team — implementing that check is your responsibility, not the caller's.

4. Timeouts, Cancellation, and Propagating Both

Every inbound request already carries a CancellationToken that fires if the client disconnects. Pass it all the way down, including into outbound calls:

public async Task<ActionResult> Get(string number, CancellationToken ct)
{
    var account = await _coreBankingClient.GetAccountAsync(number, ct);   // not CancellationToken.None
    return Ok(account);
}
A forgotten token is an invisible resource leak
Passing CancellationToken.None (or omitting it, which defaults to the same thing) means the outbound call keeps running, and keeps holding a connection and a thread, even after the original client has given up and gone away. Under load this is how a slow downstream dependency quietly degrades an otherwise healthy service.
