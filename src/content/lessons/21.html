What is a captive dependency, and which lifetime combination causes it?

1. The Shape Of A Hosted Service

StatementReconciliationJob.cs
public class StatementReconciliationJob(
    IServiceScopeFactory scopeFactory,
    ILogger<StatementReconciliationJob> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(15));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try
            {
                await RunOnceAsync(stoppingToken);
            }
            catch (Exception ex)
            {
                // one bad run must not kill the loop — log and wait for the next tick
                logger.LogError(ex, "Reconciliation run failed");
            }
        }
    }

    private async Task RunOnceAsync(CancellationToken ct)
    {
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        // ... do the work with a fresh, scoped DbContext
    }
}

// registration
builder.Services.AddHostedService<StatementReconciliationJob>();

BackgroundService runs for the lifetime of the application — which means it is registered and behaves like a Singleton. That is the whole reason this page exists right after the DI lifetimes lesson.

2. Why You Cannot Just Inject AppDbContext Here

This is the captive dependency bug, in its most common real-world form
A BackgroundService is created once and lives for the whole application. If you inject a Scoped DbContext straight into its constructor, you get one DbContext for the entire lifetime of the process — every run shares the same change tracker, memory grows unbounded, and eventually you hit stale data or disposed-object exceptions. The fix is always the same: inject IServiceScopeFactory, and create a new scope — and therefore a fresh DbContext — for each unit of work, as above.

3. Scheduling Beyond A Fixed Interval

PeriodicTimer is enough for "every N minutes." For anything calendar-shaped — "2am daily," "first of the month," "skip weekends" — reach for a library rather than hand-rolling date math:

ToolUse for
PeriodicTimer / BackgroundServiceSimple fixed-interval work, in-process, no external dependency
Quartz.NETCron-style schedules, persisted job state, misfire handling
HangfireFire-and-forget or delayed jobs triggered from request code, with a dashboard

4. Make Every Run Safe To Repeat

A job host can restart mid-run — a deployment, a crash, a scale-down. Design every job as if it might run twice on the same batch:

  • Track processed items by a unique key (statement ID, transaction reference) and skip ones already marked done.
  • Prefer "claim a batch, then process it" over "process everything untouched," so two overlapping runs do not double-handle the same rows.
  • Make the final write (marking something processed) the last thing that happens, after the real work succeeded — never before.

5. Logging Every Run, Not Just Failures

A job that runs silently in the background is invisible until it breaks, and by then you often cannot tell how long it has been broken. Log the start, the count processed, and the duration of every run — not just exceptions — so "did last night's reconciliation actually run?" has an answer in the logs instead of a guess.
