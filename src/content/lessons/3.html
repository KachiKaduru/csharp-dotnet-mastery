Recall first — no notes
Name three value types and three reference types. What happens when you assign one reference-type variable to another?

1. Conditionals

nothing surprising here
if (balance >= amount)
    Withdraw(amount);
else if (balance > 0)
    Console.WriteLine("Insufficient funds");
else
    Console.WriteLine("Account empty");

var status = balance > 0 ? "active" : "empty";   // ternary

One difference from C and from JavaScript: the condition must be a bool. if (count) and if (customer) do not compile. Write if (count > 0) and if (customer is not null). This removes a whole family of truthiness bugs.

2. Loops

four forms
for (int i = 0; i < 10; i++) { }              // known count

foreach (var account in accounts) { }          // every item — the default choice

while (queue.Count > 0) { }                    // check first

do { attempt++; } while (attempt < 3);         // body runs at least once

Prefer foreach. It cannot run off the end of the collection, it reads better, and it works on anything implementing IEnumerable<T> — including things with no index at all, like a HashSet or a lazily-produced sequence.

You cannot modify a collection while iterating it
Adding to or removing from a collection inside its own foreach throws InvalidOperationException: "Collection was modified; enumeration operation may not execute." Iterate a copy (foreach (var x in list.ToList())), collect the items to remove and delete them afterwards, or use RemoveAll with a predicate.

break leaves the loop, continue skips to the next iteration. C# has no labelled break — to leave nested loops either extract a method and return, or set a flag. Extracting the method is almost always clearer.

3. The switch Statement

the classic form
switch (status)
{
    case "active":
        EnableTransactions();
        break;                    // required — C# forbids silent fall-through
    case "dormant":
    case "frozen":                // stacking empty cases IS allowed
        BlockTransactions();
        break;
    default:
        throw new ArgumentException($"Unknown status: {status}");
}

Unlike C and Java, C# does not permit implicit fall-through. Every non-empty case must end with break, return or throw, or it will not compile. The accidental-fall-through bug is impossible.

4. The switch Expression

This is the modern form and the one you should reach for. It is an expression — it produces a value — so it assigns directly:

the same logic, as an expression
var fee = accountType switch
{
    "savings"  => 0m,
    "current"  => 50m,
    "corporate" => 250m,
    _          => throw new ArgumentException($"Unknown type: {accountType}")
};

Three things to notice:

  • _ is the discard pattern — the default case.
  • No break, no case keyword. Arms are pattern => value, comma-separated.
  • It must produce a value on every path, so the compiler warns if your arms are not exhaustive. That warning is the feature: adding a new account type makes the compiler point at the code you forgot.

5. Pattern Matching

Patterns are where this stops being syntax sugar. They let you test shape, type and value together.

type patterns
// test the type and bind a variable in one step
if (payment is CardPayment card)
    Console.WriteLine(card.Last4);          // card is strongly typed in here

// the older, clumsier equivalent
if (payment.GetType() == typeof(CardPayment))
{
    var c = (CardPayment)payment;           // test, then cast separately
    Console.WriteLine(c.Last4);
}
relational and logical patterns
var band = amount switch
{
    < 0           => "invalid",
    0             => "zero",
    > 0 and <= 1000    => "small",
    > 1000 and <= 100_000 => "medium",
    _             => "large"
};

if (code is 401 or 403)         // 'or' pattern beats code == 401 || code == 403
    return "unauthorised";

if (customer is not null)       // the idiomatic null check in modern C#
    Process(customer);
property patterns — the genuinely powerful one
var decision = transfer switch
{
    { Amount: <= 0 }                      => "reject: invalid amount",
    { Source.Currency: "NGN", Amount: > 1_000_000 } => "refer: large local transfer",
    { Source: { IsFrozen: true } }        => "reject: source frozen",
    { Source.Id: var s, Target.Id: var t } when s == t => "reject: same account",
    _                                     => "approve"
};

Read that as a rules table rather than as code. Each arm states a shape the object might have. when adds an arbitrary condition, and var s binds a value for use in that condition. Written as nested if statements this would be twenty lines and considerably harder to check for correctness.

Why this matters beyond elegance
Business rules — which is most of what enterprise code is — are naturally a table of conditions mapped to outcomes. Pattern matching lets you write them as a table, so a reviewer can check the rules against a specification line by line instead of tracing branches. That is a correctness benefit, not just a readability one.
