1. The DbContext

AppDbContext.cs
public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Account> Accounts => Set<Account>();
    public DbSet<Transaction> Transactions => Set<Transaction>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Account>(e =>
        {
            e.HasKey(a => a.Id);
            e.Property(a => a.Number).IsRequired().HasMaxLength(20);
            e.HasIndex(a => a.Number).IsUnique();
            e.Property(a => a.Balance).HasPrecision(18, 2);     // money: always set this
            e.HasMany(a => a.Transactions)
             .WithOne(t => t.Account)
             .HasForeignKey(t => t.AccountId);
        });
    }
}

// registration — Scoped by default, which is what you want
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
Always set precision on money columns
Without HasPrecision(18, 2) the provider picks a default, which on SQL Server is decimal(18,2) but elsewhere may silently truncate or round. EF warns about this at startup. Set it explicitly on every monetary column.

2. A DbContext Is A Unit Of Work

This is the mental model that makes everything else make sense. A DbContext tracks every entity it loads, notices what you change, and writes all of it when you call SaveChangesAsync.

no UPDATE statement anywhere
var account = await _db.Accounts.FirstAsync(a => a.Number == number, ct);

account.Balance += 500m;            // just a property assignment

await _db.SaveChangesAsync(ct);     // EF works out the UPDATE and runs it

And because it is one unit of work, SaveChangesAsync is a single transaction. Several changes either all commit or all roll back:

atomic by default
source.Balance -= amount;
target.Balance += amount;
_db.Transactions.Add(new Transaction { /* ... */ });

await _db.SaveChangesAsync(ct);     // all three, or none

That is why a DbContext is registered Scoped and must never be a Singleton: it is per unit of work, it is not thread-safe, and a long-lived one accumulates tracked entities until it becomes both slow and wrong.

3. Querying

LINQ becomes SQL
// translated to SQL and executed in the database
var rich = await _db.Accounts
    .Where(a => a.Balance > 1_000_000m)
    .OrderByDescending(a => a.Balance)
    .Take(10)
    .ToListAsync(ct);

// projection — selects only these columns
var names = await _db.Accounts
    .Where(a => a.Status == AccountStatus.Active)
    .Select(a => new { a.Number, a.Owner })
    .ToListAsync(ct);

// read-only: skip change tracking for a measurable speedup
var report = await _db.Accounts.AsNoTracking().ToListAsync(ct);
Where the query runs is everything
// GOOD: filter runs in SQL, 10 rows come back
var a = await _db.Accounts.Where(x => x.Balance > 1_000_000m).ToListAsync();

// CATASTROPHIC: ToListAsync first, so the whole table is loaded into memory
var b = (await _db.Accounts.ToListAsync()).Where(x => x.Balance > 1_000_000m);
Both compile. Both return the same answer. The second pulls every row across the network and filters in your process — fine against 50 rows in development, fatal against 5 million in production. Everything before ToListAsync becomes SQL; everything after it is LINQ-to-objects.

4. The N+1 Problem

The single most common EF performance bug, and it is invisible in a small dataset.

one query, then one per row
var accounts = await _db.Accounts.ToListAsync(ct);          // 1 query

foreach (var a in accounts)
    Console.WriteLine(a.Transactions.Count);                 // 1 query EACH

1,000 accounts means 1,001 round trips. With lazy loading enabled it happens silently; without it you get a null or empty collection instead, which is at least noticeable.

the fix
var accounts = await _db.Accounts
    .Include(a => a.Transactions)        // one query with a join
    .ToListAsync(ct);

// better still if you only need a count — let the database count
var summary = await _db.Accounts
    .Select(a => new { a.Number, TxCount = a.Transactions.Count() })
    .ToListAsync(ct);
Log the SQL in development
o.UseSqlServer(cs).LogTo(Console.WriteLine, LogLevel.Information);
You cannot reason about an ORM you cannot see. Turn this on, exercise an endpoint, and count the queries. N+1 is obvious the moment the SQL is visible, and invisible otherwise.

5. Migrations

terminal
dotnet tool install --global dotnet-ef

dotnet ef migrations add AddAccountStatus    # generate from model changes
dotnet ef database update                    # apply to the database
dotnet ef migrations remove                  # undo the last, if not applied
dotnet ef migrations script                  # SQL for a DBA to review

A migration is a generated, reviewable, source-controlled description of a schema change. Read every one before applying it — EF occasionally decides to drop and recreate a column, which is a data-loss event.

Do not auto-migrate production
Database.Migrate() at startup is convenient in development and dangerous in production: concurrent instances race, and a failure happens during deployment with no rollback. Generate a script, review it, apply it as a deliberate deployment step.

6. When Not To Use EF

EF is excellent for the common case: load an object graph, change it, save it. It is the wrong tool for:

  • Bulk operations. Updating a million rows one tracked entity at a time is pathological. Use ExecuteUpdateAsync, ExecuteDeleteAsync, or raw SQL.
  • Complex reporting queries. Window functions, CTEs, hints. Write the SQL — use Dapper or FromSqlRaw.
  • Stored procedures. Common in bank and enterprise systems, where the procedure is the contract.

Mixing is normal and sensible: EF for domain operations, Dapper or raw SQL for reports and bulk work. Reaching for raw SQL is not an admission of defeat.
