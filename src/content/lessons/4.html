1. A Class

Account.cs
public class Account
{
    private decimal _balance;                 // field: the actual storage

    public string Number { get; }             // property, read-only
    public string Owner { get; set; }         // property, read-write

    public Account(string number, string owner, decimal opening)
    {
        Number = number;
        Owner = owner;
        _balance = opening;
    }

    public decimal Balance => _balance;       // computed property

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        _balance += amount;
    }
}

var acct = new Account("0123456789", "Ada", 5000m);
acct.Deposit(500m);
Console.WriteLine(acct.Balance);   // 5500

Conventions worth adopting now because every C# codebase uses them: PascalCase for types, methods and properties; camelCase for locals and parameters; _underscoreCamelCase for private fields. Unlike Java, method names are capitalised.

2. Properties — The Important Part

Java convention is a private field plus getBalance() and setBalance(). C# makes this a language feature, which means you can start with a plain property and add logic later without changing a single caller.

the progression
// 1. auto-property: compiler generates the hidden backing field
public string Owner { get; set; }

// 2. same public shape, now with validation — callers unchanged
private string _owner = "";
public string Owner
{
    get => _owner;
    set => _owner = string.IsNullOrWhiteSpace(value)
        ? throw new ArgumentException("Owner is required")
        : value.Trim();
}

// 3. computed — no storage at all
public bool IsOverdrawn => _balance < 0;

value is a contextual keyword inside a setter — it is the incoming assignment. You never declare it.

Why this matters for design
In Java, exposing a public field and later needing validation is a breaking change, so the defensive habit is to write getters and setters for everything up front. In C# a property is the public surface, so you write { get; set; } and add behaviour behind it whenever you actually need it. Less ceremony, same encapsulation.
FormMeaning
{ get; set; }Read and write
{ get; }Settable only in the constructor or an initialiser
{ get; private set; }Public read, writable only inside the class
{ get; init; }Settable only during object construction — then frozen

3. Constructors and Object Initialisers

three ways to build an object
// classic constructor
public Account(string number) => Number = number;

// primary constructor (C# 12) — parameters available throughout the class body
public class Customer(string name, string email)
{
    public string Name { get; } = name;
    public string Email { get; } = email;
}

// object initialiser — set properties after construction, in one expression
var c = new Customer("Ada", "ada@example.com")
{
    // any settable property can go here
};

// required: compiler enforces it was set, without needing a constructor
public class Config
{
    public required string ConnectionString { get; init; }
    public int Timeout { get; init; } = 30;
}

var cfg = new Config { ConnectionString = "..." };   // omit it and this will not compile

required plus init is a very useful pairing: the compiler guarantees the property was supplied, and nothing can change it afterwards. It gives you immutability and validated construction without writing a constructor.

Prefer constructors for invariants
If an object is meaningless without certain values, take them as constructor parameters — then no code path can produce an invalid instance. Object initialisers are convenient but run after the constructor, so validation inside the constructor cannot see them.

4. static

belongs to the type, not an instance
public class AccountNumberGenerator
{
    private static int _counter;                      // one copy, shared
    public static int Issued => _counter;

    public static string Next() => $"ACC{++_counter:D8}";
}

var n = AccountNumberGenerator.Next();    // called on the type

// a static class cannot be instantiated — for pure helpers
public static class MoneyFormatter
{
    public static string ToNaira(decimal amount) => $"₦{amount:N2}";
}
Static mutable state is a trap
_counter above is shared by every thread in the process. In a web application that means concurrent requests racing on the same variable, producing duplicate account numbers under load. Static methods with no state are fine. Static mutable data needs synchronisation, or it needs to not be static.

5. ToString, and Printing Objects

override it on anything you will log
public override string ToString() => $"Account {Number} ({Owner}): {Balance:N2}";

The default ToString() prints the type name, which is useless in a log line. Override it on your domain types — but be deliberate: whatever you put in ToString() will end up in log files, so leave out anything sensitive.

6. Equality

By default, two class instances are equal only if they are the same object. For types that represent a value, that is usually wrong:

reference equality by default
var a = new Account("0123456789", "Ada", 100m);
var b = new Account("0123456789", "Ada", 100m);

a == b        // false — different objects
a.Equals(b)   // false — same reason

You can override Equals and GetHashCode to fix this, and they must agree — two objects that are equal must return the same hash code, or dictionaries and sets will lose them. The next page covers record, which generates both correctly and makes this problem mostly disappear.

The contract, in one line
Equal objects must have equal hash codes. Break that and HashSet will hold duplicates while Contains returns false for an item that is demonstrably in there — with no exception to tell you.
