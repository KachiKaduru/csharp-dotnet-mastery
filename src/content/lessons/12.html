1. A Controller

AccountsController.cs
[ApiController]
[Route("api/[controller]")]                      // → api/accounts
public class AccountsController : ControllerBase
{
    private readonly IAccountService _service;

    public AccountsController(IAccountService service) => _service = service;

    [HttpGet("{number}")]                        // GET api/accounts/0123456789
    public async Task<ActionResult<AccountResponse>> Get(
        string number, CancellationToken ct)
    {
        var account = await _service.FindAsync(number, ct);
        return account is null ? NotFound() : Ok(account.ToResponse());
    }

    [HttpPost]                                   // POST api/accounts
    public async Task<ActionResult<AccountResponse>> Open(
        OpenAccountRequest request, CancellationToken ct)
    {
        var account = await _service.OpenAsync(request, ct);
        return CreatedAtAction(nameof(Get), new { number = account.Number },
                               account.ToResponse());
    }
}

[ApiController] is doing real work: it binds the request body automatically, and it returns 400 with a validation problem document before your method runs if the model is invalid. You do not write if (!ModelState.IsValid).

2. Minimal APIs

Same framework underneath, less ceremony. Good for small services and for endpoints with no real logic.

Program.cs
app.MapGet("/health", () => Results.Ok(new { status = "healthy" }));

app.MapGet("/api/accounts/{number}", async (
    string number, IAccountService service, CancellationToken ct) =>
{
    var account = await service.FindAsync(number, ct);
    return account is null ? Results.NotFound() : Results.Ok(account.ToResponse());
});

Note that IAccountService is injected straight into the lambda — parameters are resolved from the route, the query string, the body or the DI container as appropriate.

ChooseWhen
Minimal APIsSmall services, health checks, thin endpoints, highest throughput
ControllersMany related endpoints, shared filters, conventional structure a team already knows

3. Status Codes That Matter

CodeMeansReturn it when
200 OKSuccess with a bodyGET, or an update returning the new state
201 CreatedResource createdPOST that created something. Include a Location header
204 No ContentSuccess, nothing to sayDELETE, or an update returning nothing
400 Bad RequestThe request is malformed or invalidValidation failure. The client must change something
401 UnauthorizedNot authenticatedNo or invalid credentials. Badly named — it means unauthenticated
403 ForbiddenAuthenticated but not permittedIdentity known, permission denied
404 Not FoundNo such resourceUnknown id
409 ConflictConflicts with current stateDuplicate creation, concurrent-edit clash

500 Server ErrorWe brokeNever deliberately. Never with a stack trace
401 vs 403, since everyone gets this wrong
401 means "I do not know who you are" — authenticate and try again. 403 means "I know exactly who you are and you may not do this" — retrying will not help. The names are historically backwards; the meanings are not.

4. DTOs — Never Expose Your Entities

separate request, response and domain
// what the client may send
public record OpenAccountRequest(string Owner, string Currency, decimal Opening);

// what the client gets back — note what is absent
public record AccountResponse(string Number, string Owner, decimal Balance, string Status);

// your entity, which stays internal
public class Account
{
    public int Id { get; set; }                  // internal key
    public string? InternalRiskGrade { get; set; }
    public string? KycDocumentPath { get; set; }
    // ...
}
Three reasons this is not optional
Over-posting: binding directly to an entity lets a client set any property — including Balance or IsAdmin — by adding it to the JSON. Leakage: serialising an entity exposes internal columns, and EF navigation properties can drag whole object graphs into the response. Coupling: your API contract becomes your database schema, so a column rename is a breaking API change.

Records are ideal for DTOs: immutable, value-equal, and concise. One line per contract.

Mapping entities to DTOs without drowning in boilerplate

Once you have a few entities and a few DTOs each, hand-written mapping code multiplies fast. Two honest options:

manual — a static method or extension
public static class AccountMappings
{
    public static AccountResponse ToResponse(this Account a) =>
        new(a.Number, a.Owner, a.Balance, a.Status.ToString());
}
AutoMapper — convention-based
builder.Services.AddAutoMapper(typeof(Program));

CreateMap<Account, AccountResponse>();   // property names match → wired automatically

var response = _mapper.Map<AccountResponse>(account);
Which to reach for
Manual mapping is explicit, debuggable, and shows up in "find usages" — prefer it while a codebase is small or the mapping has real logic (computed fields, conditionals). AutoMapper earns its keep once you have dozens of DTOs and the mappings are genuinely one-to-one; past that point it removes a lot of repetitive, low-value code. Either way, never let a mapping library silently expose a field you meant to hide — a renamed entity property that happens to match a DTO property will map automatically, which is convenient until it leaks something.

5. Validation

data annotations
public record OpenAccountRequest
{
    [Required, StringLength(100, MinimumLength = 2)]
    public required string Owner { get; init; }

    [Required, RegularExpression("^[A-Z]{3}$", ErrorMessage = "Currency must be a 3-letter code.")]
    public required string Currency { get; init; }

    [Range(0, 1_000_000_000)]
    public decimal Opening { get; init; }
}

With [ApiController], a failure returns 400 and a ValidationProblemDetails body listing each bad field — automatically, before your code runs.

Annotations handle shape. Business rules do not belong here — "the source account must have sufficient funds" needs the database and belongs in your service, returning a domain result the controller translates.

6. Error Handling In One Place

Program.cs — translate once, not per controller
app.UseExceptionHandler(handler =>
{
    handler.Run(async context =>
    {
        var ex = context.Features.Get<IExceptionHandlerFeature>()?.Error;
        var logger = context.RequestServices.GetRequiredService<ILogger<Program>>();

        logger.LogError(ex, "Unhandled error on {Path}", context.Request.Path);

        var (status, title) = ex switch
        {
            AccountNotFoundException   => (404, "Account not found"),
            InsufficientFundsException => (409, "Insufficient funds"),
            ArgumentException          => (400, "Invalid request"),
            _                          => (500, "An unexpected error occurred")
        };

        context.Response.StatusCode = status;
        await context.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = status,
            Title = title,
            // deliberately NOT ex.Message for the 500 case
            Instance = context.Request.Path
        });
    });
});

That pattern-matching switch is the Week 1 material doing real work. Benefits: consistent error shape everywhere, one place to change, controllers free of try/catch, and internal exception text never reaches a client — which matters, because exception messages leak table names, file paths and connection details.

ProblemDetails is a standard
RFC 7807 defines a conventional JSON error shape: type, title, status, detail, instance. ASP.NET Core produces it by default for validation failures. Use it for your own errors too, and clients can parse every error the same way.
