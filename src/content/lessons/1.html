Recall first — no notes
From the previous page: what are the two compilation steps between Program.cs and running code, and what does the CLR do?

1. Check What You Have

terminal
dotnet --version      # SDK version
dotnet --list-sdks    # every SDK installed
dotnet --list-runtimes
dotnet --info         # everything, including the OS and architecture it detected

Install the SDK, not the runtime. The runtime only runs .NET apps; the SDK includes the compiler and the CLI, and contains a runtime anyway.

SDK vs runtime
A machine that only runs deployed apps needs the runtime. A machine you develop on needs the SDK. If dotnet --version works but dotnet build complains about no SDK, you installed the wrong one.

2. Your First Project

terminal
dotnet new console -o HelloApp   # create a console project in ./HelloApp
cd HelloApp
dotnet run                       # restore, build, and run in one step

That is the whole loop. dotnet run does three things — restores NuGet packages, compiles, and executes — which is convenient and occasionally confusing, because a failure could come from any of the three.

Useful templates:

CommandProduces

dotnet new webapiASP.NET Core HTTP API

3. What Got Generated

HelloApp/
├── Program.cs          ← your code
├── HelloApp.csproj     ← the project definition
└── obj/ and bin/       ← build output. Never commit these
HelloApp.csproj
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
</Project>

The .csproj is the equivalent of a pom.xml, and it is strikingly short because the SDK supplies sane defaults and every .cs file in the folder tree is included automatically. You do not list source files.

SettingMeaning
OutputTypeExe for a runnable app, Library for a .dll
TargetFrameworkWhich .NET version to build against — net8.0, net9.0
NullableNullable reference types. Leave this on — see the types page
ImplicitUsingsAdds common using directives automatically, which is why Console works with no using statement

4. Program.cs and Top-Level Statements

A new console project gives you one line:

Program.cs — modern
Console.WriteLine("Hello");

That is top-level statements. The compiler wraps it in a class with a Main method for you. Older code, and anything that needs explicit control, looks like this instead:

Program.cs — explicit, still valid
namespace HelloApp;

class Program
{
    static void Main(string[] args)
    {
        Console.WriteLine("Hello");
    }
}

Both compile to effectively the same thing. Know the second form exists — you will meet it constantly in existing codebases and in older documentation.

One restriction worth knowing
A project can have only one file with top-level statements. The compiler needs exactly one entry point, and a second such file is a compile error rather than a warning.

5. The Commands You Will Actually Use

terminal
dotnet restore              # download NuGet packages
dotnet build                # compile
dotnet run                  # restore + build + run
dotnet test                 # run tests
dotnet clean                # delete bin/ and obj/
dotnet publish -c Release   # self-contained output ready to deploy

dotnet watch run            # rebuild and restart on every file save

dotnet watch run is the one that changes your day. Save a file and the app restarts — and for ASP.NET Core it will often hot-reload without even restarting.

Debug vs Release
Debug is the default: no optimisation, full debug symbols, useful stack traces. Release optimises and strips debug detail. Benchmark in Release only — timing a Debug build produces numbers that mean nothing.

6. Solutions — Grouping Projects

One project is a unit of compilation. A solution (.sln) is just a list of projects that belong together, so you can build and test them as a set.

terminal
dotnet new sln -n MiniBank
dotnet new classlib -o MiniBank.Core
dotnet new webapi   -o MiniBank.Api
dotnet new xunit    -o MiniBank.Tests

dotnet sln add MiniBank.Core MiniBank.Api MiniBank.Tests

# make Api and Tests able to use Core
dotnet add MiniBank.Api/MiniBank.Api.csproj reference MiniBank.Core/MiniBank.Core.csproj
dotnet add MiniBank.Tests/MiniBank.Tests.csproj reference MiniBank.Core/MiniBank.Core.csproj

dotnet build    # from the solution folder: builds everything

That three-project shape — domain library, API, tests — is the conventional starting layout for a service, and worth getting used to early.

7. NuGet

terminal
dotnet add package Serilog
dotnet add package Dapper --version 2.1.35
dotnet list package                    # what this project references
dotnet list package --outdated
dotnet remove package Serilog

The command edits your .csproj, adding a PackageReference:

<ItemGroup>
  <PackageReference Include="Serilog" Version="4.1.0" />
</ItemGroup>

Packages are cached per user, not per project — under ~/.nuget/packages. The same role as the local Maven repository, and the same occasional need to clear it.

9. Do This Now

  1. Run dotnet --info and note your SDK version and target framework.
  2. Create a console app, run it, and open the .csproj. Identify all four properties.
  3. Rewrite Program.cs from top-level statements into an explicit class Program with Main. Confirm it still runs.
  4. Build the three-project solution from section 6 and run dotnet build from the solution folder.
  5. Add a package, look at what changed in the .csproj, then remove it.
