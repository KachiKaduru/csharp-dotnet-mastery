Recall first — no notes
Why can an auto-property gain validation later without breaking callers? And what does required guarantee?

1. Inheritance

base and derived
public class Account
{
    public string Number { get; }
    public decimal Balance { get; protected set; }

    protected Account(string number) => Number = number;

    public virtual decimal MonthlyFee() => 0m;         // virtual: can be replaced
}

public class CurrentAccount : Account
{
    public CurrentAccount(string number) : base(number) { }   // call the base constructor

    public override decimal MonthlyFee() => 50m;              // override: replace it
}

C# uses : for both inheritance and interface implementation, where Java uses extends and implements. Single inheritance only — one base class, any number of interfaces.

2. virtual, override, new and sealed

This is a real difference from Java and a common source of silent bugs for people arriving from it.

In C#, methods are NOT virtual by default
In Java every method can be overridden unless marked final. In C# the base method must be explicitly virtual (or abstract), and the derived method must say override. Forget either and you do not get an override — you get a new, unrelated method that hides the base one, and calls through a base-typed reference will run the base version. The compiler warns; the warning is easy to miss.
KeywordMeans
virtualDerived classes may replace this
overrideThis replaces a virtual or abstract base member
abstractNo implementation here; derived classes must provide one
sealedNo further overriding (on a member) or inheriting (on a class)
newDeliberately hide the base member. Rarely what you want

3. Abstract Classes

shared state plus a required hole
public abstract class Payment
{
    public decimal Amount { get; init; }
    public DateTime CreatedUtc { get; } = DateTime.UtcNow;    // shared state

    public abstract string Process();                          // each type must supply this

    public string Summary() => $"{GetType().Name} of {Amount:N2}: {Process()}";
}

public class CardPayment : Payment
{
    public required string Last4 { get; init; }
    public override string Process() => $"charged card ending {Last4}";
}

An abstract class cannot be instantiated. Use one when derived types genuinely share state or implementation, not merely a shape.

4. Interfaces

a contract with no state
public interface IPaymentProcessor
{
    Task<bool> ProcessAsync(decimal amount);
    string Name { get; }
}

public class CardProcessor : IPaymentProcessor
{
    public string Name => "Card";
    public Task<bool> ProcessAsync(decimal amount) => Task.FromResult(true);
}

Interface names conventionally begin with I — a convention, not a rule, but universal in .NET.

Abstract classInterface

The practical rule
Prefer interfaces and composition. Inheritance couples a derived type to its base permanently, and deep hierarchies become difficult to change precisely because the coupling is invisible at the call site. Interfaces give you the polymorphism without the coupling — which is also what makes code testable, since you can substitute a fake implementation. Reach for an abstract class only when there is real shared implementation to inherit.

5. Records

A record is a class the compiler writes for you, designed for data. One line replaces about forty:

records
public record Money(decimal Amount, string Currency);

var a = new Money(100m, "NGN");
var b = new Money(100m, "NGN");

a == b                  // TRUE — value equality, generated for you
Console.WriteLine(a);   // Money { Amount = 100, Currency = NGN }

var c = a with { Amount = 250m };   // copy with one change; a is untouched

The compiler generates a constructor, read-only properties, Equals, GetHashCode, ToString, and the with expression — all correct, all consistent with each other.

Use aWhen
recordThe type is its data: DTOs, API requests and responses, events, value objects, configuration
classThe type has identity and behaviour that changes over time: a service, a repository, an entity whose balance mutates
structSmall, short-lived values where allocation matters. Measure before choosing this
This is where the equals/hashCode problem goes away
The previous page warned that Equals and GetHashCode must agree or collections lose your objects. A record generates both from the same components, so they cannot disagree. For value-like types, using a record is not just less typing — it eliminates the bug.

You can add members to a record like any type, and validate in the body:

a record with behaviour
public record Money(decimal Amount, string Currency)
{
    public bool IsZero => Amount == 0m;

    public Money Add(Money other) => other.Currency != Currency
        ? throw new InvalidOperationException("Currency mismatch")
        : new Money(Amount + other.Amount, Currency);
}
